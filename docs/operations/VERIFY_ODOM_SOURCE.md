## 一、为什么做这个测试

### 1.1 直接动机

M3 阶段要做 EKF 融合的 A/B 对比：

- **A 组**：纯 `/odom`（差速插件输出的里程计）
- **B 组**：`/odometry/filtered`（robot_localization 融合后的输出）
- **真值**：`/gazebo/model_states`（Gazebo 世界位姿）

这个对比成立的前提是「**A 组是一个会漂的估计值**」。如果 A 组本身就是真值，那它误差恒为 0，B 组最好也只能追平，**实验从设计上就不成立**。

### 1.2 触发线索

2026-11-09 受控直行测试中机器人翻倒，翻倒后 `/odom` 出现 `z = 0.0396`（高度非零）。

**轮式编码器积分在数学上不可能产生 z 分量**——它只知道轮子转了多少弧度，二维平面上做差速运动学推算，z 恒为 0。能报出 z 的只有一种可能：**直接读取模型的世界三维位姿**。

这条旁证很强，但只是"翻倒时的异常值"，缺乏正面确认。因此需要一次正常行驶条件下的对照测试。

### 1.3 为什么不能用 `strings` 代替

`strings` 只能证明「插件支持这个参数」，不能证明「实际运行走的是哪一支」。默认值是什么、URDF 没写时回落到哪，都必须靠实测。

## 二、预期目标

### 2.1 要回答的问题

**车正常行驶、位置和朝向都显著偏离原点后，`/odom` 与 `/gazebo/model_states` 的位姿是否仍然完全一致？**

### 2.2 判据设计（测试前就定好，避免事后找理由）

| 预期现象 | 判定 |
|:---|:---|
| `diff` 的 `x/y/z/yaw` 全部为 0，且车已离开原点 | `/odom` = WORLD（真值），A 组不成立 |
| `diff` 有可见偏差，`z` 恒为 0 | `/odom` = ENCODER（编码器积分），A 组可用 |
| `z` 不为 0 | 直接证明读的是世界位姿（轮子算不出高度） |
| 只有 `yaw` 有偏差、`x/y` 全零 | 位置取自世界、姿态另有来源，需再查 |

### 2.3 精度门槛

关键是**精度量级**，不是"看起来差不多"。

编码器积分的误差来源：
- 每帧乘法（轮速 × 轮半径 × 时间）都有浮点舍入
- 每次物理步进存在微小滑移
- 误差逐帧累积

跑 2~5 米、经历上千个物理步之后，x、y、yaw **三个量同时精确到 0.1 mm / 0.01°**，在编码器积分路径上几乎不可能发生。

因此判据设为：**小数点后四位（0.1 mm 与 0.01°）完全一致**。达到这个精度就不是"接近"，而是"同源"。

### 3.4 取数命令（终端 B）

```bash
cd ~/ros2_ws && source install/setup.bash && python3 -c "
import rclpy, math, time
from nav_msgs.msg import Odometry
from gazebo_msgs.msg import ModelStates

def yaw(q):
    return math.degrees(math.atan2(2*(q.w*q.z + q.x*q.y), 1 - 2*(q.y*q.y + q.z*q.z)))

rclpy.init()
n = rclpy.create_node('peek_pose')
d = {}

def on_odom(m):
    d['odom'] = m

def on_gt(m):
    for i, name in enumerate(m.name):
        if 'basic_diff_drive_robot' in name:
            d['gt'] = m.pose[i]

n.create_subscription(Odometry, '/odom', on_odom, 10)
n.create_subscription(ModelStates, '/gazebo/model_states', on_gt, 10)

t0 = time.time()
while time.time() - t0 < 10 and len(d) < 2:
    rclpy.spin_once(n, timeout_sec=0.1)

if len(d) < 2:
    print('[FAIL] 未收齐，缺: %s' % (', '.join(k for k in ('odom','gt') if k not in d)))
else:
    o = d['odom'].pose.pose
    g = d['gt']
    print('odom  x=%+.4f y=%+.4f z=%+.4f yaw=%+.2f' % (o.position.x, o.position.y, o.position.z, yaw(o.orientation)))
    print('gt    x=%+.4f y=%+.4f z=%+.4f yaw=%+.2f' % (g.position.x, g.position.y, g.position.z, yaw(g.orientation)))
    print('diff  x=%+.4f y=%+.4f z=%+.4f yaw=%+.2f' % (o.position.x-g.position.x, o.position.y-g.position.y, o.position.z-g.position.z, yaw(o.orientation)-yaw(g.orientation)))
rclpy.shutdown()
"
```

**为什么用这个脚本而不是三条 `echo`**：

| 手工 `echo` 的缺陷 | 本脚本的处理 |
|:---|:---|
| `model_states` 返回数组，混着家具，要人工数下标 | 按 `name` 字符串匹配，自动筛出机器人 |
| 四元数 `(x,y,z,w)` 人眼读不出朝向，要手算 `atan2` | 自动换算成 `yaw`（度） |
| 三条命令之间有数百毫秒连接延迟，运动中等价 0.1~0.4 m 假误差 | 两话题同时订阅，同一时刻收齐后再打印 |

### 3.5 测试纪律（三条硬约束）

1. **必须等车完全停稳**。行驶中取数会引入帧间不同步，污染"是否完全一致"这个判断。
2. **必须离开原点 0.5 m 以上**。停在原点时两者当然一致，测不出任何东西。
3. **至少取两次，且位置、朝向明显不同**。单点样本无法排除巧合。

### 4.2 数据汇总

| 次数 | 位置 (x, y) | 距原点 | yaw | diff |
|:---:|:---|:---:|:---:|:---|
| ① | (1.9194, 0.9795) | 2.15 m | 7.93° | 全 0 |

### 4.3 两个关键细节

**① 两次采样的位置与朝向完全不同**

两点相距 2.93 m，yaw 从 7.93° 变到 82.00°（差 74.07°）。在这种差异下两次 `diff` 都是零，排除了"某一点恰好对齐"的巧合解释。

**② 第 2 次的 `-0.0000` 反而强化了证据**

`y`、`z` 显示为 `-0.0000`（浮点负零），含义是"差值是一个极小负数，四舍五入到四位小数后为零"。残差量级约 `1e-5 ~ 1e-4` 米（0.01~0.1 mm）。

如果 `/odom` 是从 `model_states` 复制同一份数据，符号应当一致。出现负零说明这是**两个独立发布的量**，只是数值上精确到 0.1 mm 一致。这比"完全相同"更有说服力——它证明了两条独立数据链路，却收敛到同一结果。


关键输出（mangled name 已翻译）：

三条结论：

| 证据 | 含义 |
|:---|:---|
| `UpdateOdometryWorld()` 与 `UpdateOdometryEncoder()` **同时存在** | 插件有两套独立实现，运行时按枚举值二选一 |
| 字符串 `odometry_source` 出现在二进制中 | 插件确实读取该 SDF 标签，不是猜测 |

### 4.5 URDF 现状核对

`urdf/parts/plugins.urdf.xacro` 中 `gazebo_ros_diff_drive` 插件块只有：


**`<odometry_source>` 标签不存在**，插件走自身默认值。ROS2 版源码读取该参数的形式为 `Get<int>("odometry_source", static_cast<int>(OdomSource::WORLD))`，**默认值即 `WORLD`**。

URDF 未写 + 默认 WORLD + 实测行为吻合 —— 三条互证，逻辑闭环。

## 五、结论判定

### 5.1 最终结论

**`/odom` 的数据源是 `WORLD`，即直接读取模型的世界位姿，不是编码器积分。**

证据链（四条互不依赖）：

1. 两次不同位置、不同朝向下 `diff` 全零（0.1 mm / 0.01° 精度）
2. 编码器积分在数学上无法达到该精度（上千步累积必然产生厘米级误差）
3. `z` 分量随物理状态实时变化（正常时 0，翻倒时 0.0396）—— 轮式里程计不可能产生 z
4. 插件二进制含 `UpdateOdometryWorld()` / `UpdateOdometryEncoder()` 双分支 + 默认值 `WORLD` + URDF 未显式指定

### 5.2 推翻的既有认知

**2026-11-08 日志中「`odometry_source` 走默认 ENCODER」的记载错误**，应更正为 WORLD。

### 5.3 对 M3 实验设计的影响

| 影响 | 说明 |
|:---|:---|
| **A 组不成立** | 纯 `/odom` 误差恒为 0，与 EKF 无可比性；原设计的"融合改善精度"曲线无法画出 |
| 13% 位移缺口获得新解释 | 昨天 EKF 输出位移仅为 odom 的 87%，原假设是"丢测量/协方差近奇异"；现在更合理的解释是**输入为完美测量导致滤波器退化**，与 `sensor_timeout` 无关 |
| IMU 补噪声升级为必要项 | 从"让数据更真实"的优化项，变为"让滤波器能正常工作"的必要条件 |

### 5.4 对既有基线数据的影响（范围超出 M3）

`nav2_params_hybrid.yaml` 中 AMCL 的 `odom_topic: /odom`。由于 `/odom` = 真值，等价于 **AMCL 一直在使用完美里程计做粒子传播**，`map→odom` 几乎无需修正，定位误差趋近于 0。

推论：**已有 16 个有效 bag 与批量实验的成功率、路径偏差等指标，均建立在"机器人永远知道自己在哪"的前提上，属于乐观上界，不能直接作为真实场景表现写入报告。**

这一条同时是方法论层面的可写入材料的发现：*仿真默认配置下里程计等价于真值，导致导航评估系统性偏乐观。*

### 5.5 修复方向（✅ 已于 2026-11-10 执行，复测结果见第七节）

在 `plugins.urdf.xacro` 的 `<publish_odom>true</publish_odom>` 后加：

```xml
<odometry_source>0</odometry_source>
```

`0 = ENCODER`，`1 = WORLD`。

**必须用整数 `0`，不能写 `ENCODER`**：源码用 `Get<int>()` 解析，字符串会解析失败，而 Gazebo 的 `Get<int>` 在失败时**静默返回默认值 WORLD**，表现为"改了、build 了、重启了，行为一点没变且无任何报错"。

改后需 `colcon build --packages-select pkg03_gazebo_20260814`（`urdf/` 在 install 列表内，launch 读 `install/` 副本）并重启仿真，再按本文第三节流程复测。

### 5.6 预期复测结果与已知局限

> ⚠️ **本节为测试前的预测，已被 2026-11-10 实测推翻，见 7.7。原预测保留不删，用于对照"当初的假设与错误原因"。**

**原预测**：`diff` 从"精确 0"变为**非零但极小**（毫米量级纯数值积分误差），且 `z` 恒为 `0.0000`。

**原判断的局限（重要）**：当时认为 Gazebo 中轮子默认不打滑，轮子转角与位移近乎完美对应。因此推断切到 ENCODER 后**仍然不会出现"越跑越漂"的累积误差曲线**，跑 5 米可能只差几毫米。

**实测结果**：跑 3.07 m 位置误差 0.343 m（11.2%），跑 5.10 m 位置误差 1.252 m（24.5%），比预测大两个数量级。**"轮子不打滑"这个前提本身是错的**（原因见 7.7）。

**仍然成立的部分**：A 组此前缺少可对比误差来源这一判断成立，只是补足方式不需要额外调摩擦——切换 ENCODER 后打滑误差已经出现。

### 7.6 误差性质初步分析：横向占绝对主导

把误差向量投影到**真值车头方向**上拆成纵向（沿车头）与横向（垂直车头）两个分量：

| 轮次 | 纵向分量 | 横向分量 | 横向占误差比例 |
|:---:|:---:|:---:|:---:|
| ① | −0.071 m | +0.335 m | **98%** |
| ② | +0.372 m | +1.195 m | **95%** |

（两分量平方和等于总误差平方，可自行校验）

两轮都是横向占绝对主导，这个一致性是关键：

- 若误差源于**轮径/轮距标定错**，应表现为**纵向**偏（走多了或走少了）
- 若误差源于**航向估偏**，应表现为**横向**偏，且随行驶距离放大

实测是后者。配合 `yaw` 误差同号为正（odom 认为转得比实际更多），指向**转弯时驱动轮空转导致航向多估**。

**直观类比**：闭着眼走路，每转一个弯都比实际多转几度。走远了不会觉得"路程算错"，而是整个人偏到旁边——位置误差几乎全在横向，量级远大于纵向。

**这条对 M3 的意义**：航向漂移恰好是 IMU 陀螺仪能修正的部分（陀螺测真实角速度，不受轮子打滑影响）。因此 A/B 对比有明确且可预期的方向：

```
A 组（纯 odom）      ：航向靠轮子积分 → 打滑即漂 → 横向误差累积
B 组（EKF 融合 IMU）：航向靠陀螺仪   → 不受打滑影响 → 横向误差被压住
```

### 7.7 与 5.6 预期不符的原因（更正记录）

5.6 原预测"误差毫米级，跑 5 米约差 3 mm"，实测跑 3 m 差 343 mm，**大两个数量级**。

**错误根源：假设"Gazebo 轮子默认不打滑"，该前提不成立。**

实际打滑来源：

| 因素 | 具体值 | 影响 |
|:---|:---|:---|
| 万向轮摩擦 | `caster.urdf.xacro` 中 `mu1=mu2=0.1` | 为顺滑滚动刻意设低，但也使支撑轮在转弯时侧向约束弱 |
| 驱动轮扭矩上限 | `max_wheel_torque=20` | 对 0.12 kg 的轮子属严重过配，指令一变即容易超出发/地附着极限 |
| 车身质量轻 | 轮子 0.12 kg、电机 0.15 kg、万向轮 0.05 kg | 正压力小，可用摩擦力上限低 |

结果：**转弯时驱动轮空转**，编码器把"轮子转过的角度"当作"车实际位移"，误差被逐段放大。直行时纵向误差小（7.6 表中纵向分量仅 −0.07 / +0.37 m），转弯时横向误差大，与该机理吻合。

**因此不需要额外降低摩擦来"制造"误差** —— 现有配置已自带可观的打滑误差。

### 7.8 待查：误差的超线性增长

| 量 | ① → ② 倍数 |
|:---|:---:|
| 真值距原点 | 1.66× |
| 位置误差 | **3.65×** |
| yaw 误差 | **11.1×** |

距离只增 66%，航向误差扩大 11 倍，**不是线性累积**。两种互斥解释：

| 解释 | 含义 | 如何区分 |
|:---|:---|:---|
| (a) 两轮在**同一仿真会话内连跑** | 误差跨轮累积，40° = 第一轮 3.6° + 第二轮路径累积 | 若未重启，超线性合理 |
| (b) 每轮都**重启仿真** | 40° 在单轮内产生，说明该轮发生异常（卡住空转 / 大幅转向 / 碰撞） | 需查 Nav2 日志有无 `Spin` / `Backing Up` / `Clearing costmap` 等恢复行为 |

**本次未记录两轮之间是否重启仿真，故不下定论。** 该问题已转入第八节待办。

### 7.9 本阶段对 M3 的结论

| 项 | 状态 |
|:---|:---|
| A 组是否为真值 | ✅ 已解决，不再是真值，会漂 |
| 误差是否有物理来源 | ✅ 有，转弯空转导致航向多估 |
| IMU 能否改善 | ✅ 有明确预期方向（修航向 → 压横向误差） |

## 九、2026-11-23 追加：`wheel_separation` 几何错误与旋转比例误差定案

### 9.1 本节的缘起

第七节的 7.8 遗留了「航向误差超线性增长（11.1 倍）」这一未决问题，D-03 / D-04 计划用「纯直行」「多距离取数」来区分打滑与累积漂移。**实际上根因不是打滑，是差速插件的 `wheel_separation` 配错了 1.5 倍**，所以无论怎么测都会指向「转弯打滑」，D-03 / D-04 的判据本身设错了。

### 9.2 几何核对

| 依据 | 值 |
|:---|:---|
| `model.xacro` 左右轮组挂载 | `y = ±0.12` |
| `wheel.urdf.xacro` 轮心相对轮组再外移 | `motor_l/2 + shaft_length + wheel_length/2 = 0.03+0.02+0.01 = ±0.06` |
| 轮心实际位置 | `±(0.12+0.06) = ±0.18` |
| **接触点实际间距** | **0.36** |
| 插件 `wheel_separation`（修正前） | **0.24**（差 1.5 倍） |
| 插件 `wheel_diameter` | 0.10，与 `wheel_radius 0.05` 一致 |

### 9.3 机理（与第七节的对应关系）

`sep` 同时出现在两处，故一个错误同时污染两个方向：

```
反解轮速：v_L = v - w*sep/2 ,  v_R = v + w*sep/2   ⇒ sep 小 ⇒ 物理转向速率 = 指令的 2/3
积分航向：th = (d_R - d_L)/sep                      ⇒ sep 小 ⇒ odom 航向 = 真值的 1.5 倍
```

第七节 7.6 / 7.7 观察到的「转弯航向多估、横向误差主导」，正是这 1.5 倍比例误差的体现，而非轮胎打滑；7.8 的「超线性」则是两轮路径转向量不同导致的放大差异。轮径自洽，所以**直线不受影响**，这也解释了为什么 7.3 的直线段误差量级正常。

### 9.4 实测取证（`scripts/odom_spin_probe.py`）

发布 `/cmd_vel` 角速度 0.5 rad/s 持续 2 s，同时采 `/odom` 与 `/gazebo/model_states`：

| 量 | 修正前（预期） | 修正后（实测） |
|:---|:---:|:---:|
| `odom / 真值` | 1.500 | **1.055** |
| `真值 / 指令` | 0.667 | **0.955** |
| `odom / 指令` | 1.000 | 1.008 |
| 真值转角（指令 57.3°） | ~38° | **54.7°** |
| odom 转角 | ~57° | **57.8°** |

修正后残余 5.5%（`odom/真值`）为 Gazebo 真实轮胎滑移，属正常量级。**结论：旋转比例误差已从 50% 降至 5.5%，`wheel_separation` 错误是主因。**

### 9.5 处置与影响

- 修复：`urdf/parts/plugins.urdf.xacro` `wheel_separation 0.24 → 0.36`，`colcon build --packages-select pkg03_gazebo_20260814` 后重启 Gazebo 生效。
- `worlds/one.world` 内也有 0.24，但该 world 无任何引用（实际用 `robocup_home.world` + `spawn_entity` 注入 xacro），死副本，未动。
- **对既有数据**：AMCL 对照实验 A~D 四组的 **yaw 类指标全部失效**（输入自带 50% 比例误差）；位置类指标不受影响。见 [AMCL_PARAM_SWEEP_ARCHIVE.md](file:///home/robot/ros2_ws/docs/AMCL_PARAM_SWEEP_ARCHIVE.md) 4.5。
- **第八节待办状态更新**：D-03 / D-04 **作废**（判据基于错误前提）；其目标（区分打滑与累积漂移）已由本节探针一次性回答。D-01（漂移曲线）仍可做，但需在 `sep 0.36` 的新基线上重新采集。

### 9.6 一个遗留观察

`odom / 指令 = 1.008`，说明编码器忠实反映了轮子转动的量；`真值 / 指令 = 0.955`，说明车实际少转 4.5%。这 4.5% 是滑移，其随转向角速度、地面摩擦、负载的变化尚未量化，若后续做 EKF 对比需要更精细的 odom 误差模型，可再测几组不同 `wz` 下的比值。
